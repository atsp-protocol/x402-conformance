# Cross-SDK parity

`x402conf parity` sends one vector set to the official x402 libraries for TypeScript, Python and Go, and records
how each one answers. It compares each library's answer with the outcome the spec calls for, and with the other
libraries' answers. It compares implementations against the spec and against each other. It is not certification:
a library that agrees with the vectors is not certified, and a divergence is a difference to look at, not a verdict.

## Run it

From a checkout of this repository, with Node 20 or later, Go 1.24 or later and Python 3.10 or later:

```
PYTHONPATH=src python3 -m x402conf parity --sdk ts,python,go --upstream-pin $(cat docs/parity/pin) --offline --out parity.json
python3 tools/parity_report.py --validate parity.json
python3 tools/parity_report.py --divergences parity.json
```

The first run prepares each harness: `npm ci` in `ts/parity-harness/`, a virtualenv with the pinned Python package
under `~/.cache/x402conf-parity/` (`--cache` moves it), and `go build` in `examples/go/parity/`. Preparing downloads
the pinned packages. Running the vectors uses no network. `--root` points at the checkout when you run from elsewhere.

## The pin

`docs/parity/pin` holds one upstream commit of `x402-foundation/x402`. `docs/parity/pins.json` gives the version of
each library at that commit and the release that published it:

| SDK | package | version |
|---|---|---|
| TypeScript | `@x402/core`, `@x402/evm`, `@x402/express` | 2.28.0 |
| Python | `x402` with the `evm`, `flask` and `httpx` extras | 2.25.0 |
| Go | `github.com/x402-foundation/x402/go/v2` | v2.28.0 |

Each harness reports the version it actually loaded, and `--validate` refuses a run whose version is not the pinned
one or whose pin is not `docs/parity/pin`.

## The vectors

`docs/parity/vectors.json` is generated by `ts/parity-harness/src/make-vectors.ts` and is the same file on every
run. Each vector has an id, tags, a spec anchor and an expected outcome.

- `verify` vectors go to the library's facilitator verify, with the `exact` EVM scheme registered for
  `eip155:84532` only: malformed payloads, an unregistered network of the same family and of another namespace, a
  wildcard requirement, a payload whose network differs from the requirement, over- and underpayment, recipient,
  expiry and signature mismatches, an unsupported scheme and version, and a requirement with no EIP-712 domain.
- `paid-route` vectors go to the library's payment middleware, serving `GET /paid` on loopback, as the
  `PAYMENT-SIGNATURE` header: not base64, base64 of text, of an array, a number, `null`, an empty object, and an
  object with only `x402Version`.

Every vector names a check id from `docs/check-ids.json` whose anchor pins a line of the spec, or is labelled
`security-profile`. Expected reason codes are the codes in section 9 of the x402 V2 specification. The signed
vectors use a key derived from a public label in the generator: it has never been funded and is not used on any
network, and only signatures are stored.

## What a harness does

Each harness reads the vectors on stdin and answers one line per vector: `status` and `content_type` for a paid
route, `isValid` and `invalidReason` for verify, and `threw` when the library raised or threw instead of answering.
Go returns a `*VerifyError` as its normal rejection, which is recorded as `isValid: false`; any other error is
recorded as `threw`.

- No chain and no key. The signer is a stub: `getCode` answers "no code", so a signature is recovered locally; every
  other read fails; every write (a transaction) is refused and counted. A run in which the signer was asked to write
  is invalid.
- No network. The facilitator the payment middleware needs is a recording double on loopback, started by the
  runner, which never approves anything. Each harness refuses and counts any connection to an address other than
  loopback: a preloaded guard on `net` sockets and DNS for Node, on `socket` for Python, and on the default HTTP
  transport, the facilitator client and the resolver for Go. Go has no process-wide socket hook, so a library that
  builds its own transport is outside the Go guard. A run with any refused attempt is invalid.

`tests.test_parity.NoNetwork` proves both: a run has no outbound attempt and no write, and with `--probe-outbound`
each harness tries one connection to `192.0.2.1:80`, which its guard refuses and counts, and `--validate` then
refuses the run.

## Faults

`--fault` is a self-test of the oracle. `status` and `swallow-reason` substitute the library's decision at the
harness boundary: a paid route's 4xx becomes 500, or a rejection loses its `invalidReason`. They do not rebuild the
library. `wildcard-network` registers two networks of the `eip155` family, so the TypeScript and Go libraries derive
the `eip155:*` pattern themselves. The Python library derives that pattern from a single registration, as discussed
in x402-foundation/x402#3936, so its fault run and its control run match.

`tests.test_parity.FaultsCaught` proves that each fault is reported as a divergence, with the vector id and anchor,
for every SDK, that it changes only the vectors on its path, and that a harness that ignored the fault would fail.

## Report and evidence

`tools/parity_report.py --evidence evidence/parity parity.json` writes `evidence/parity/<pin>/run.json`, with every
divergence, and its `SHA256SUMS`. `--check evidence/parity` verifies the hashes and that the recorded divergences are
the ones the vector set gives.
